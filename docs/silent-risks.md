# 静默风险清单

**会报错的问题不可怕，不报错的才是。**

这份清单只按一个维度分类：**出问题时会不会有动静。** 报错、返回 `error`、测试变红
——都算有动静。而下面这些的共同点是：**结果照样产出，看起来完全正常。**

分三档：

- **已修** —— 曾经存在，已由某个版本消除。留在这里是因为它们各自代表一类形态
- **仍在（有意的）** —— 已知、已权衡、写明代价的取舍
- **仍在（未知的）** —— 证据不足，代码里不臆造

---

## 一、已修：它们当初为什么没被发现

| 缺陷 | 静默在哪 | 怎么发现的 | 修于 |
|---|---|---|---|
| **开仓挂单不计入全仓合并查档** | 币种级 `mmr` 算小了 → 保证金率**偏高 12%** → 全仓强平比真实的晚触发。数字全程合理 | 专门构造跨档 straddle（持仓在一档、加上挂单才越界）。此前的样本里持仓与挂单都在二档，两种解释给出同一个数 | v0.9.7 |
| **保证金率分子漏扣挂单手续费** | 同上，同一方向偏乐观。旧样本残差 `2e-4`，被判为「取数时点」 | 把挂单放大到持仓的 19 倍，让两个候选公式的差远超噪声 | v0.9.8 |
| **小数指数随部分平仓无界增长** | **结果完全正确**，只是回测越跑越慢。40 轮后系数 825 位 | 下游报的 CPU profile。本仓的基准跑得短，看不出来 | v0.9.5 |
| **精度水位线不回落** | 净持仓归零会重置仓位的指数，于是**均值回复的策略里它看起来永远正常**；真正记账的是现金，而现金的指数是历史最深值的水位线，永不痊愈 | 上一条修完后追问「为什么下游的形态和我的不一样」 | v0.9.6 |
| **强平罚金按错档位** | 只在「平仓量 ≠ 保留量」时才显形。逐仓那次样本两者相等，三种解释同值 | 全仓那次真实爆仓（减 17577 张、留 8000 张）把它们分开了 | v0.9.9 |
| **全仓一律全平，不走阶梯减仓** | 偏保守——高估爆仓杀伤力。回测跑得出结果，只是过于悲观 | 等到一次真实的全仓爆仓 | v0.9.9 |
| **缺标记价时静默退回最新成交价** | 强平判据用成交价，**插针会扫掉本不该爆的仓位**。对尾部风险就是强平的策略这是假阴性——参数组合被淘汰，扫描结果里不留痕迹 | 下游提出。见 `TestMarkPxFallbackLiquidatesOnAWick` | v1.0.0 翻默认值 |
| **对拍测试零次迭代也会绿** | 夹具被清空或 JSON 字段改名导致反序列化成 `nil`，循环一次不执行，**一条真实数据都没核对** | 下游分享的同类失效模式（4000 组随机参数只撞出 2 次目标分支） | v0.9.6 |
| **`SetLeverage` 不更新已有仓位的 `Lever`** | 设定值与仓位值悄悄分岔，依赖它的初始保证金/收益率/强平价全停在旧值 | 实测改杠杆行为时顺带撞见 | v0.9.2 |

### 两条方法论，比上表任何一条都通用

**1. 阴性结果不能当阳性用。**
本仓曾在模拟盘上测「标记价与成交价是否同深」，两条一起返回空，读成了「一样深」，
实际是「一样取不到」。**「两条都取不到」和「两条一样深」在数据上长得一模一样。**

由此的自查：模拟盘上测出的「历史深度 / 最早时间 / 总条数」，多个不相干的序列给出
同一个边界是警报——**但齐断本身不足以定罪，还要看齐断的位置**是否恰好等于某个
整齐的时间点、且与数据自身的节奏对得上。资金费那条也齐断，复核后是真的（277 条
× 8h = 92 天，正好对上滚动窗口）。

**2. 最直接的读数往往不是最可靠的判据。**
一次 API 抖动返回「持仓 0 个」，差点被报成「仓位没了」；起疑是因为**账单和现金都
纹丝不动**。可靠的往往是那个「不该变的量没变」。

这一条有个更锋利的版本，来自 okx-api-v5-go 复核标记价边界时的自查：
**读数正确不代表方法正确。** 他们发布的日期是对的，但那是因为机器时区恰好是
UTC+8——`Candle.Time()` 按 Go 惯例返回本地时区，同一份代码换到 UTC 机器上会打印
出差一天的日期，**而且完全察觉不到**。可靠的判据是原始毫秒时间戳，不是格式化后的
字符串。

由此得一条可操作的：**任何「读出来是对的」都要问一句「换个环境还对吗」**——
时区、locale、机器字长、默认精度，都是这类隐含输入。

**3. 三件事收在一处：证据链里有一环是被推定的，而不是被检验的。**

这三次都不报错，因为被推定的那一环**恰好各自成立或恰好不影响当前结论**：

| 推定了什么 | 实际 | 怎么暴露的 |
|---|---|---|
| 「跨指数的代价随差值增长」 | 是个台阶，不是斜坡 | 改了两版都没效果，最后靠微基准 |
| 「两条序列都返回空 = 一样深」 | 是「一样取不到」 | 换个环境（生产）重测 |
| 「当前状态是对的 = 过去没说过某句话」 | 记录才是判据 | 对方留了原文 |
| 「零强平的配置验出逐位等价 = 判据改动无影响」 | 那个配置根本碰不到被改的路径 | 自己回头查路径覆盖 |

最后一条是 okx-grid-strategy 验 v1.0.1 时的自我更正，也是本仓发布说明写错的那次
（见 [roadmap.md](./roadmap.md) 的更正条目）。

**可操作的一条**：下结论前问「这条证据**排除了**哪些可能」，而不是「这条证据
**支持**什么」。「测出来是对的」通常两者都答不了。

---

**4. 「我早就想过了」的地方，值得回去看一眼当初想的是什么。**

前三条讲的是「证据链里有一环没验证」。这一条不同：**结论当时是成立的，后来条件变了
——或者它从一开始就只是个假设，被当成了决定。**

三个实例，本仓两个：

| | 当初 | 后来 |
|---|---|---|
| README 里「全仓强平尚未实测、阶梯减仓未建模」 | 属实 | **v0.9.9 已实测并实现，README 两个版本没跟上** |
| fidelity 里「罚金按减仓后档位算」 | 当时的最佳解释 | v0.9.9 改成「按平掉的张数」，**旧那条没删，与新那条并列在同一张清单里** |
| 下游把 `report/` 放进依赖守卫的排除名单 | 一个「决定」 | 实际是个**从没验过的假设**；它当时恰好干净，但**「恰好干净」与「被守住」是两回事** |

还有一层，来自下游的自我观察：**给别人的建议，自己往往不会拿去验**——提建议时人在
「解释」的模式里，不在「检验」的模式里。本仓那条「判 `r != CancelUser` 即可」正是
这么写出来的，而它在本仓自己的库里同样是错的。

**可操作的一条**：修好一个东西之后，搜一遍**所有**提到它的地方，而不只是你当时改的
那一份文档。本仓这两处都是「改了三份文档、漏了 README 和另一份清单」。

**5. 引用别人的测量，等于引用了它的全部前提——而前提通常不写在数字旁边。**

同一个事实（标记价的历史边界）被更正过三次，每次错在**不同的前提**上：

| 错在哪 | 表现 |
|---|---|
| 环境 | 模拟盘上量的，两条一起返回空被读成「一样深」 |
| **粒度** | 1D 上量出「2020-01-01」，下游在 1m 上照用，差了 8 天 16 小时 |
| 对齐 | 港时只对标记价成立，成交价落在 UTC 日界上 |

**证据本身没错，错在它被搬到了一个它没覆盖的场景里。** 与第四条（「我早就想过了」）
的区别在于：那条是条件随时间变了，这条是**从一开始就有一组没写下来的适用条件**。

可操作的两条：

- **发布一个测量时，把测量条件写在数字旁边**——环境、粒度、时区对齐、样本量。
  写在别处等于没写，因为搬运的人只搬数字
- **传递边界值时给原始时间戳**，别给格式化后的日期。本仓的时区那次和粒度这次，
  都是格式化把前提抹掉了

## 二、仍在：有意的取舍

| 项 | 静默行为 | 为什么留着 | 怎么关掉 |
|---|---|---|---|
| **`Bar.Funding` 留空 = 不计资金费** | 系统性**高估多头持仓收益**，不报错 | 历史费率只有约 3 个月（**已在生产环境复核**），超窗口不可避免；且造成的是连续偏差而非离散事件。按「降级的两只手」落在「允许但写明」那一只 | 自行接第三方数据源，逐步传 `Funding` |
| **`Metrics.MgnRatio` 与强平判据在 `1e-20` 上可能不一致** | 判据用精确比较（`权益 ≤ 分母`），而 `MgnRatio` 是先除再报的，商在 `1+1e-25` 处会被舍成恰好 1 | 判据要准，`MgnRatio` 只是展示值。真分歧时**精确比较是对的那个** | 无需关闭；读判据不要读比率 |
| **不建模部分成交** | 挂单要么全成要么不成 | 没有深度数据，凭空模拟部分成交是臆造 | 无 |
| **`Simulator` 非并发安全** | 同一个实例被多 goroutine 用会数据竞争 | 文档写明由调用方保证；单线程回测不需要锁的代价。**「多实例并存 + 共享只读快照」这一形态已由外部实测，见下** | 一个 goroutine 一个实例 |
| **每根 K 线重算一次强平阈值** | 不是错误，是成本：子步数远多于成交数时，约 99.94% 的重算是白做的 | 缓存它要靠「写 `s.pos` 的每一处都更新」这个人工维护的不变式，破了会无声地用过期阈值判强平。**明确选择承受这个成本**，决策记录见 [roadmap.md](./roadmap.md) | 无 |
| **模拟盘的规格与档位表与生产不同** | 用模拟盘数据跑生产回测，结果整体偏移且不报错 | 本库不选数据源。见 `okx-rules.md §10` | 用生产的 `refdata.Snapshot` |

### 并发：已验证的与未验证的

本仓这台机器没有 C 编译器，`go test -race` 跑不起来——这是本仓自己够不着的一块。
由 okx-grid-strategy 在 MinGW-W64 / CGO_ENABLED=1 下代跑：

| 形态 | 结果 | 说明 |
|---|---|---|
| 全量单测 | 0 竞态 | **这份几乎不说明任何事**——他们的测试基本是单 goroutine 的，竞态检测只报实际发生过的竞争，没有并发就必然全绿 |
| **8 个 goroutine × 68 次完整回测**，各持独立 `*Simulator`，**共享同一份 `refdata.MustEmbedded()` 快照**；每次 43,200 根 K 线 ≈ 16 万子步 | **0 竞态** | 这份才是有效的：若本仓有包级可变状态、或 `Snapshot` 里有惰性初始化的缓存，这个形态会撞上 |

**覆盖边界**：验的是「多实例并存 + 共享只读快照」，**不覆盖「同一个 `Simulator`
实例被多 goroutine 使用」**——那本来就不受支持。

对方主动指出第一份是「假绿」并补跑了第二份，这个动作本身值得记：
**竞态检测的绿，取决于测试有没有真的制造并发。**

## 二·五、跨库静默：本库报了，下游不看就会错

这一类与上面两节**性质不同**：本库工作完全正常，该报的都报了，`error` 也返回了。
静默发生在**交界处**——调用方没读那个字段，于是一个错误的结论被产出且毫无动静。

写下来是因为它查起来最难：本库这侧的测试全绿，下游这侧的结果看起来也正常。

| 情形 | 本库做了什么 | 下游不看会怎样 |
|---|---|---|
| **强平价够不着** | `LiqPx` 留零（价格要跌到负数才触及，OKX 同样返回空串） | `if px <= m.LiqPx { 告警 }` **永远不触发**——一条风控分支从此再没进去过 |
| **该币种没有全仓仓位** | `MgnRatio` 留零，另给 `HasPosition = false` | `if ratio < 1.5 { 告警 }` **一直在响**——方向与上一条相反，同样静默 |
| **强平前撤单** | 各 `Liquidation.CanceledOrders` 列出被撤的委托 ID，同时以 `CancelLiquidation` 出现在 `Canceled` 中 | **已确认发生过**：一个下游的阶梯网格在被清算后的空簿上按旧层号重挂，以为自己还持有目标仓位。它的执行层读了 `Canceled`，**是策略层只处理了「资金不足」那几种，漏了强平这一类** |
| **缺指数价，`index` 型算法委托无从判断** | 生成一条 `AlgoTrigger`，`Reason` 说明原因、`OrdID` 为空 | 遍历 `AlgoTriggers` 而不看 `Reason` 的，会把**没触发**读成触发 |

### 第三条的根因值得单独说：漏接枚举值没有任何提示

那个下游的执行层**读了** `Canceled`，问题出在策略层——两族网格共用一套执行端，
却各自处理事件，而其中一族只列举了「资金不足」那几种原因。

**Go 不会为此报错**：接口只管方法签名，不管你有没有处理某个枚举值。这类漏接既不
编译失败也不运行时告警，只是某一类事件从此被无声丢弃。

可操作的两条：

- **把纪律换成工具**：`golangci-lint` 的 `exhaustive` 检查器能在 `switch` 漏掉某个
  取值时报错。对「撤单原因」这类枚举，那比靠人记得可靠得多
- **列「无害」而不是列「有害」**：用 `Reason.AffectsAccountState()`。它的实现是
  白名单——列出只影响单笔委托的那几种，其余（含**日后新增的任何取值**）一律当作
  账户级。方向是刻意的：新值总落进未列举的那一侧，而我们要它落进安全那一侧

  > 本仓最初给下游的建议是「判 `r != CancelUser` 即可」，**那是错的**：这些取值里
  > 有三种不是使用者撤的、却只影响那一笔委托（只挂单会成交、立即成交类没成交、
  > 触发时资金不足）。按那个判据，网格会在**第一次挂单被拒时就停机**——而那是
  > 必然发生的事。是下游指出来的，本仓的库里同样会踩。
  >
  > 判据的全部理由是**代价不对称**：把账户级当无害的，策略在不存在的前提上继续跑
  > 且不报错；把无害的当账户级的，多做一次重新同步——有代价，但看得见。

### 前两条是同一个形态：零值不是「安全的默认」

它们对应 okx-tickflow-go 那边的 NaN 陷阱——「与 NaN 比较永远是 false，一个分支从此
再没进去过」。本库不用 NaN（`decimal` 没有），但**零值在阈值比较里扮演了同一个角色**：

    LiqPx = 0    ->  多头永远「还没跌到」，告警永不触发
    MgnRatio = 0 ->  永远「低于任何阈值」，告警永远在响

两者都不报错，且方向相反——所以「零值到底安不安全」这个问题**没有统一答案**，
只能逐个字段看语义。

**怎么避免**：先判存在性再比数值。`Metrics` / `CrossMetrics` 都带 `HasPosition`，
`LiqPx` 的「无定义」也在字段注释里写明。规则是：**判断「有没有」的那个字段，
永远不要用「值等不等于零」去代替。**

## 三、仍在：未知的

| 项 | 不确定的是什么 | 当前行为 | 影响方向 |
|---|---|---|---|
| **多个全仓仓位时先减哪一个** | 实测那次该币种下只有一个仓位 | 按 `(instId, posSide)` 排序取第一个可降档的，使结果可复现 | 未知；单仓位时无差异 |
| **费率组优先级** | 现有数据下两条解析路径给出同一个数 | 有守卫测试，两条路径开始分歧时报警 | 当前无差异 |

## 怎么用这份清单

- **接入前**读第二节：那些是你会默认承受的偏差
- **结果可疑时**读第一节：看看形态是否似曾相识
- **提 issue 时**：如果发现了一个「不报错但结果不对」的行为，它属于这份清单，
  优先级高于任何会报错的问题

每一条的证据与重跑方式在 [`okx-rules.md`](./okx-rules.md)，按证据等级标注
（实测 / 文档 / 未定）；有效性边界见 [`fidelity.md`](./fidelity.md)。
