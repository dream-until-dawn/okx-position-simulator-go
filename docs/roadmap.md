# 版本排期

范围与决策依据见 [design.md](./design.md)，规则依据见 [okx-rules.md](./okx-rules.md)。

## 分支与发布约定

| 分支 | 角色 |
|---|---|
| `main` | 只接受来自 `dev` 的合并，每次合并打 `vX.Y.Z` tag，保持永远可 `go get` |
| `dev` | 默认开发分支，日常提交落这里 |
| `feat/*` `fix/*` | 仅当改动会持续多天且打断 dev 时才开，完事 squash 回 dev |

Go 库特有约束：

- **tag 必须打在 `main` 上**，严格 semver（`v0.1.0`），`go get` 只认这个
- **v1.0.0 之前 API 可自由变更**（v0 不受兼容性承诺约束）——要充分利用这个窗口把 API 打磨定型
- 一旦发布 `v2`，module path 必须加 `/v2` 后缀。**因此 v1.0.0 是一道必须谨慎跨过的门**

## 已完成的版本

### v0.1.0 —— 规则数据层

超出初稿的部分：`refdata/live` 的定期自动拉取与**规则变更检测**、费率表的
`WithRate` / `WithLevel` 覆盖、确定性快照持久化、`cmd/refdata-sync`。

### v0.2.0 —— 逐仓永续核算

买卖模式与开平仓模式**都已支持**（原计划只做前者，但仓位状态机同时处理两者
几乎不增成本，且模拟盘账户本身就是开平仓模式，对拍需要）。

公式一律先在模拟盘标定再写代码，这一版标定出的规则见
[okx-rules.md](./okx-rules.md) 各节。

### v0.3.0 —— 预下单计算与内置撮合

内置撮合最实在的价值是**成交角色由模拟器判定**：挂住后被触发是 maker，
下单即成交是 taker，这一项直接决定手续费。手工灌 `Fill` 的路径继续完整可用。

### v0.4.0 —— 资金费与逐仓强平

强平的结算方式曾按「成交于费后破产价、罚金为零」建模，净效果与真实一致但四个
字段全对不上。照一次真实强平重写后才对齐——这件事直接催生了「净效果相同不等于
字段相同」这条设计原则。

### v0.5.0 —— 全仓

先在模拟盘标定再写代码这一条，这一版的回报最大。全仓与逐仓不是同一套账务的参数
差异，而是两套记账方式，凭推断几乎必错。超出初稿的收获：

- **档位表的键必须带 `instType`**。原以为同一 `instFamily` 下永续与交割合并查档，
  实测两者的一档上限折合标的币差 8 倍、mmr 差一倍、杠杆上限差 2.5 倍——不可能是
  同一条阶梯。此前 README 与 `TierKey` 的注释都写错了，已改正
- **全仓强平价有闭式解**，且是逐仓公式的推广；但没有逐仓那一个 tickSz 的缓冲
- **`bePx`（盈亏平衡价）** 顺手标定出来了，与 OKX 逐位相同
- **`MaxSize` 在全仓下少扣了一项**，高估最多 3.3 倍——这是标定过程中发现的既有缺陷，
  不是新功能
- 修掉 `BalanceView.IsoUpl` 误填 `Upl` 的问题：此前两者恒等，有全仓后才会分离

### v0.8.0 —— 对拍加固与差异清零

这一版的起点是发现**第一条验收标准从未被真正验证过**。design.md 写着「所有输出
结构体与 OKX v5 REST 响应字段级同构」，而对拍工具比的是手挑的十几个字段——挑着比
永远发现不了「有个字段我压根没建模」。

新的 `view` 模式与 OKX 的**原始 JSON** 逐字段比对。首跑 184 个字段，暴露 35 处差异、
4 处未分类，其中三类是真错：

- **零与空串搞混**。OKX 两者含义不同且并不一致：仓位的 `liqPenalty`/`pnl`/`fundingFee`
  没有时是 `"0"`，`imr`/`liqPx` 没有时是空串；余额的 `imr`/`mmr` 是 `"0"`，`mgnRatio`
  却是空串。此前一律按「零就留空」处理
- **`pnl` 一直空着**。实测 `realizedPnl = pnl + fee`，即 OKX 的 `pnl` 正是本库的毛
  已实现盈亏，`realizedPnl` 是净额——两者恰好对应 `RealizedPnl` 与 `NetRealizedPnl()`
- **`uplLastPx`/`uplRatioLastPx` 从未建模**。按最新价而非标记价的浮盈，回测以成交价
  撮合时对得上的正是这一套

关键的设计是 `policy.go`：把「不建模什么、为什么」变成显式声明，没对上又没声明的
字段直接判失败。OKX 日后新增字段也会立刻暴露。

另外发现 SDK 一直导出着通用的已签名请求 `okx.Do`，于是「逐仓保证金增减因缺少签名
方法而无法对拍」这条记载不成立，缺口随之关闭（实盘 8 字段一致）。

性能基准照出两处结构问题：`Fill` 的资金校验只要可用余额却调了完整的 `Balance`
（占其耗时 52%），而 `CrossMetricsOf` 在遍历仓位的循环里逐个重算合并张数（平方）。
修完 `Fill` 的分配次数降了一半，随仓位数的增长也从 2.05 倍压到 1.51 倍。

### v1.0.1 —— 网格回测负载下的两处热点

上游网格引擎报的 CPU profile：18 个月 1m、286 万个子步、1670 笔成交、**零全仓仓位**
的回测里，`crossMetrics` 占了全程 10.34%，而账户里一个全仓仓位都没有。

改了两处，都在逐仓路径上：

| | 基线 | 改后 |
|---|---|---|
| `BenchmarkAdvance` | 5696 ns / 63 allocs | **3260 ns / 35 allocs** |
| 相对 | — | **−42.8% / −44%** |

**一、没有全仓敞口时早退。** 省下的不是两个空循环，是尾部那几次跨指数的 decimal
加减——零值的指数是 0，而现金余额经 `div` 之后常是 −20，两者相加要先算 10^20。
上游给的补丁是另起一趟前置扫描，实测在**有**敞口时反而慢 5%（多扫一遍 `s.pos`），
改成边扫边记、档位表推迟到第一次真用上时才建。

**二、强平判据不再做除法。** OKX 的规则是「保证金率 ≤ 1」，而保证金率是
`权益 / (维持保证金 + 平仓费)`——分母恒为正，于是它与 `权益 ≤ 分母` 等价，
且**少一次 20 位舍入**。这一改既更快也更准。

顺带 `BalanceOf` 只读 `imr/mmr/保证金率`、不读强平价，把 `crossMetrics` 的 `full`
开关拆成 `withIMR` 与 `withLiqPx` 两个，让它别去算 `crossLiquidationPx`。

#### 一条记下来的负结果：统一小数指数没有用

上游量到一个有意思的事实——`shopspring/decimal` 的 `Add`/`Sub`/`Cmp` 在两边指数
不同时要先算 `10^n` 对齐，而**那笔开销是个台阶不是斜坡**：差 2 位和差 19 位一样贵，
只有归零才省。本机复现：同指数 `Cmp` **9.6ns / 0 分配**，异指数 **333.5ns / 6 分配**，
差 35 倍。

于是很自然会想「把账户内部全部量补齐到同一个指数」。**试了，更慢。** 把 `notional`
的结果补齐到 −20 之后，`Advance` 由 4401 升到 4830 ns、分配由 45 升到 52——因为
补齐本身也要算一次 `10^n`，而 `notional` 的结果主要进乘法，乘法根本不在乎指数。

结论：**补齐只在「创建一次、随后被加减比较很多次」的量上划算**，而这个热循环里的量
大多创建一次用一次。上游自己也试过两种缩小指数差的改法，一次慢 4%、一次在噪声内——
方向本身是对的，但本库没有适用的形态。记在这里，免得下次重走。

（另一条没做的路：把逐仓强平的阈值价缓存在仓位上，让每根 K 线只剩一次比较。
它能把这条路径的分配打到接近零，但要靠缓存失效的纪律，而失效漏一处正是那种
「测试全绿、实盘出错」的缺陷。在「精准优先」的前提下没有做。）

### 决策记录 · 不缓存逐仓强平阈值价

**结论：不做。** 记在这里是为了下次有人提起时不必重推一遍。

#### 提议

逐仓的强平阈值价只依赖 `avgPx` / 张数 / 保证金 / 档位率 / 费率——这些在两次成交
之间都不变。把它缓存在仓位上，每根 K 线的强平判据就只剩一次比较，这条路径的分配
能打到接近零。

#### 收益是实打实的，不是理论上的

由 okx-grid-strategy 在真实负载上量得（BTC 18 个月 1m，阶梯做多网格）：

| | |
|---|---|
| `CheckLiquidation` 占单次回测 | 23.52% |
| 调用次数 / 成交笔数 | 2,858,940 / **1,670** |
| 阈值在两次成交之间不变的比例 | **99.94%** |
| 一轮参数扫描 | 11.5 小时，其中约 **2.7 小时**花在重算一个没变过的值上 |

而这只是**一个品种、一段 18 个月的样本内**。他们后面要跑多品种、六年全量、样本外，
这个数字会翻几倍。

#### 不做的理由

**它要靠缓存失效的纪律，而失效漏一处正是「测试全绿、实盘出错」那一类缺陷。**

本库的取舍是精准优先。这条改动的失败模式恰好落在最难发现的那一格：漏一处失效，
强平会用一个过期的阈值——回测照样产出结果，数字看着完全正常，而某个本该爆的仓位
活了下来（或反之）。它属于 [silent-risks.md](./silent-risks.md) 里那一类，而那份
清单存在的理由就是**这类缺陷的代价远高于它省下的时间**。

不是「做不到」。降低风险的方案是清楚的：

- **不能用 `UTime` 当版本号**——同一毫秒内的多笔成交会撞号，而网格把一根 1m
  拆成 3.64 个子步、一根线穿好几层，撞号很常见
- 需要另加一个单调计数器，并在**写 `s.pos` 的每一处**递增
- 守卫是现成的：`TestLeanLiquidationCheckAgreesWithMetrics` 扫强平边界两侧
  121 个点逐点比对，缓存漏失效会红

问题在于「写 `s.pos` 的每一处」是个**靠人维护的不变式**。今天能数清，半年后加一条
新路径时未必。而它一旦破，破得无声。

#### 什么会让这个决定翻过来

- 找到一个**不依赖人工维护不变式**的写法（例如把仓位与阈值封在同一个只能整体替换
  的值里，让「改了仓位却没更新阈值」在类型上不可表达）
- 或者：有人量到这条路径在**更常见的用法**下同样是瓶颈——目前的证据全部来自
  「子步数远多于成交数」这一种负载

#### 给受影响者的话

这条对「每根 K 线拆多个子步」的策略影响最大，而那正是网格的形态。当前没有库这侧的
绕法：调用方即使自己缓存了阈值，也仍然要走 `Advance` 才能撮合。**这是本库明确
选择承受的成本，不是没注意到。**

### v1.0.0 —— 冻结

单向门跨过去了。做完的是三件：

**一、定型审查。** v0.9.0 那一版之后又加了 5 个方法与 4 处字段，没走过同一道审查。
逐个过完改了两处——`Instrument` → `InstrumentOf`（按键查询漏了 `Of`）、
`CrossMetrics.OrderFee` → `OrderFrozenFee`（与兄弟字段 `CloseFee` 并列时分不清开仓
还是平仓）。其余七处保持原样，理由记在提交里。

**二、把命名规则做成守卫。** 此前只有「导出面有没有变」与「行情读写配不配对」两条，
「按键查询带 `Of`」一直靠人记，`Instrument` 就是这么溜过去的。补上
`TestKeyedLookupsCarryOf` 之后，三条规则都由机器管着。

**三、标记价默认必给。** 字段由 `RequireMarkPx`（默认假）反转成
`AllowMarkPxFallback`（默认假 = 必须给）——Go 的零值是 `false`，要让默认是「必须给」，
只能让字段表达【选择退出】，它同时把代价写进了名字。

这一条打断了当时唯一的外部使用者，也打断了本仓 42 个测试——**而那正是它必须在 v1.0
那一刻做的理由**。那 42 个测试全都在跑降级路径；给它们补上 `MarkPx`（取值等于 `Last`）
是行为保持的改写，只是把隐式变显式。5 个 `Advance` 示例与 README 同样补齐——
它们此前等于库自己在教降级用法。

冻结时的家底：**407 项测试、18 份真实对拍夹具、未实测清单只剩两条**
（费率组优先级在模拟盘上结构性测不了，算法委托的部分成交本库明确不建模）。

### v0.9.0 —— API 打磨

v1.0.0 是单向门：发布 v2 就得给 module path 加 `/v2` 后缀，而 v0 期间 API 可以随便
改。这一版把该改的一次改完，落到两条**可学的规则**上：

- 三对行情读写全部配对（`XxxPx` / `SetXxxPx`）。此前 `MarkPx`/`SetMark`、
  `LastPx`/`SetLast`、`IndexPx`/`SetIndexPx` 三种写法各不相同，猜 `SetMarkPx`
  会得到编译错误
- 按键查询的复合结果一律带 `Of`，返回标量的不带。`Balance` 改名成 `BalanceOf`
  还顺带消除了与 `Balance` 类型的重名——`PositionOf` 当初就是为躲这个才那么叫的

合并了 `OpenOrders` 与 `PendingOrders`（同一份数据的两个视图，用户只能靠猜），
`AlgoOrders`+`AlgoTriggerPx` 换成与 `PendingOrder` 同构的 `PendingAlgos`，
并补上按 ID 取单笔的 `PendingOrderOf` / `PendingAlgoOf`。

移除三处 v1.0 之后再也甩不掉的负担：`IsMultipleOfLot`（对 `refdata.IsMultipleOf`
的纯转发）、`MarshalPositions`（不对称，且是 6 行 json 包装）、`MarketOrdPx`
（可变的包级 var，任何 importer 都能改写）。`ComputeMetrics` 不再导出——它的签名
开发期已改过两次，导出等于永久冻结一个内部形状。

新增 `doc.go`：包级文档是 pkg.go.dev 上的第一屏，此前一直空着。

留下两条守卫：`TestExportedAPIIsFrozen` 把导出面记成金文件，任何增删改名都必须同时
改清单、从而出现在 diff 里；`TestPriceAccessorsArePaired` 保证以后加第四条行情时
不会再走样。

**后来发现守卫少了一条。** 上面两条只管住了「导出面有没有变」与「行情读写配不配对」，
而「按键查询带 `Of`」这条一直靠人记——于是 v0.9.1 加的 `Instrument(instID)` 就这么
溜了过去，形状与 `BalanceOf` 完全一样却没带 `Of`，直到 v1.0 前的定型审查才发现。
现已补上 `TestKeyedLookupsCarryOf`。

### v0.9.1 —— 外部试跑撞出来的三处缺口

以外部项目身份 `go get` 之后写了个迷你回测引擎真用一遍（读 K 线、算信号、按可用
资金定量、下单、推进、记权益曲线、跑参数扫描）。撞出三处，都补了：

- **拿不到 `Instrument`**。引擎每根 K 线都要用 `lotSz` 取整张数、`tickSz` 取整价格，
  只能自己另留一份 `RefData`。这不只是麻烦，是**正确性隐患**：两份一旦不是同一个
  （比如其中一份被自动刷新换掉），取整用的规则就和模拟器实际用的不是一套，而这种
  偏差不报错
- **没有「假设价格下的风险」**。压力测试只能改掉标记价算完再改回来。新增只读的
  `MetricsAt`
- **没有状态存档**。引擎要自己写约 18 行搬运——而我自己写那 18 行时就漏了挂单和
  算法委托。新增 `State`/`Restore`

存档那条的测试值得一提：真正要保证的性质不是「字段都对上了」，而是**恢复出来的
模拟器与原来的不可区分**。测试把两个模拟器喂同样的行情一路推下去，每一步的成交、
触发、强平、状态都必须逐字节相同——故意丢掉移动止损的极值或挂单，分别会挂掉
5 处和 7 处断言。

## 排期变更记录

按发生顺序。每条都注明缘由，便于日后判断当时的取舍是否仍然成立。

| # | 变更 | 缘由 |
|---|---|---|
| 1 | 对拍工具从 v0.8.0 **提前到 v0.2.0** | 推迟会让 v0.2 至 v0.7 全部建立在未经验证的规则理解之上；一旦某处有偏差会被单测一起固化，到 v0.8.0 才暴露时返工面积极大。v0.8.0 的职责相应改为「加固与差异清零」而非「从零建对拍」 |
| 2 | 定期自动拉取从 v0.8.0 **并入 v0.1.0** | 使用者指出 OKX 规则与用户费率等级都会变，「可定期自动拉取 + 部分参数可调」本就是规则数据层的形态。按初稿先做静态快照，后面加自动刷新时 Provider 的接口形态要重做 |
| 3 | 预下单计算与挂单冻结**提到 v0.3.0**，全仓顺延 | 使用者指出本库的核心用途是供回测引擎调用，而引擎每根 K 线都要问「这单挂得起吗、能挂多少、成交后会怎样」；追加保证金这类操作在策略回测里可能整个跑完都用不上一次。这个判断是对的——`Balance.OrdFrozen` 此前虽有字段却恒为零，是漏掉的真实缺口 |
| 4 | 撮合从「可选子包」改为**内置** | 使用者指出撮合是每个引擎都要做的事，各自重写一遍既浪费又容易在成交角色、冻结释放这类细节上出错。原 v0.6.0 的「订单层」大部分随之完成，剩余的算法单独立为 v0.7.0 |
| 5 | 资金费与强平**提到 v0.4.0**，全仓再次顺延 | 按对回测结果的扭曲程度排序：忽略资金费会系统性高估持仓收益，不模拟强平会让本该爆仓的策略产出幻想结果；全仓影响的是资金效率，量级小得多。依赖上也顺——逐仓强平是仓位级、自成一体，全仓强平是账户级，放在全仓那一版一并做 |
| 6 | v0.5.0 的验收改为**币种级**而非账户级 | 原写「全仓账户级风险指标与模拟盘一致」，实测发现 `acctLv=2` 下账户级的 `adjEq`/`availEq`/`imr`/`mmr`/`mgnRatio` **恒为空串**——风险按结算币种分别核算，不做全账户折算。跨币种折算是 `acctLv=3` 的事，本就排除在 v1.0 之外。验收标准随之改为币种级 |

| 项 | 状况 |
|---|---|
| **资金费** | 结算机制已按真实账单逐条验证，但 OKX 的历史费率只保留约 3 个月（实测四个合约全部截止在同一天，距今 97 天）。超出该窗口的回测取不到真实费率，须自行接第三方数据源、用常数近似或不计资金费。模拟器不产生费率——那是市场结果，回测预测它与预测价格无异。`Bar.Funding` 留空即不计 |
| ~~**阶梯减仓（逐仓）**~~ | **已于 2026-08-31 实测**，见 okx-rules.md §7 与 testdata/conformance/liquidation-tiered-isolated.json。真实事件照出两处此前算错的：罚金按【减仓后】档位的 mmr 率算（不是减仓前），保证金按实际盈亏/手续费/罚金扣减（不是按张数比例释放）。两处差额同源，都来自那 0.005 的率差 |

| ~~**v1.0 待办：标记价默认必给**~~ | **已于 2026-09-01 执行。** 字段由 `RequireMarkPx`（默认假）反转为 `AllowMarkPxFallback`（默认假 = 必须给标记价）——Go 的零值是 false，要让默认是「必须给」，只能让字段表达选择退出，它同时把代价写进了名字。连带改了 5 个 Advance 示例与 README，并给 42 个此前在跑降级路径的测试补上 MarkPx（取值等于 Last，行为保持不变，只是把隐式变显式）|

| ~~**阶梯减仓（全仓）**~~ | **已于 2026-09-01 实测**。全仓同样走阶梯减仓：ETH-USD-SWAP 25577 张（二档）先减到 8000 张（一档上限），90 秒后仍未获救才全平。已实现 |
| ~~**全仓强平的结算方式**~~ | **已于 2026-09-01 实测**，完整账单链 100 -> 104 -> 108（逐仓是 101 -> 105 -> 108）。损失落在现金上、封顶为该币种现金、跌破零由风险准备金补回 0。⚠️ 全仓账单的 pnl 含罚金，逐仓的不含。顺带照出罚金率此前算错：应按【本笔平掉的张数】查档 |
| ~~**挂单是否计入全仓查档张数**~~ | **已于 2026-09-01 实测**。此前测不出是样本没构造对——旧样本里持仓已在二档、挂单也按二档计。构造跨档 straddle（持仓 1900 张在一档、挂单 1000 张跨到二档）后分辨得很干净：开仓挂单按绝对值计入合并查档（残差 1.16e-7），方向不相抵，平仓挂单不计入。本库此前不计入，偏乐观，已修 |
| ~~**反向合约的资金费**~~ | **已于 2026-09-01 实测**，见 testdata/conformance/inverse-funding.json。一次结算同时拿到逐仓与全仓两条路径：金额 `ctVal × sz / 结算价 × 费率` 正向代入独立取回的费率，残差 1.9e-17 与 5.0e-17（账单字段的 16 位截断）；落点也确证——逐仓扣仓位保证金（balChg 恒为 0），全仓扣现金（balChg 等于资金费，现金核对差为 0） |
| **精度差异** | 与 OKX 的全字段对拍中，20 个字段仅差在精度：OKX 用 float64 计算并截断到 15~17 位有效数字，本库用 decimal 精确计算，相对差在 `1e-14` 量级。这类差异单独计数而不并进「一致」，是为了让它的规模一直看得见——哪天从 `1e-14` 变成 `1e-6`，说明出了别的问题 |
| **算法委托的部分成交** | 未建模触发后限价单只成交一部分时的 `partially_effective` 状态——要撞上部分成交才观察得到，而本库明确不建模部分成交（没有深度数据）。`closeFraction` 已于 2026-09-01 实测：它不是比例而是全平标志（只接受 1），且张数在触发那一刻才定，已实现 |
| **触发后的滑点** | 实测一次真实触发，成交价比触发价低一个 `tickSz`。只有一个样本，且滑点本就取决于当时的盘口深度——本库不建模它，成交价取触发价，夹具里留了守卫 |
| **费率组优先级** | 现有数据下两条解析路径给出同一个数字，无从判定。采用的是使用者拍板的选择，并有守卫测试在两条路径开始分歧时报警 |
