# 版本排期

范围与决策依据见 [design.md](./design.md)，规则依据见 [okx-rules.md](./okx-rules.md)。

## 分支与发布约定

| 分支 | 角色 |
|---|---|
| `main` | 只接受来自 `dev` 的合并，每次合并打 `vX.Y.Z` tag，保持永远可 `go get` |
| `dev` | 默认开发分支，日常提交落这里 |
| `feat/*` `fix/*` | 仅当改动会持续多天且打断 dev 时才开，完事 squash 回 dev |

Go 库特有约束：

- **tag 必须打在 `main` 上**，严格 semver（`v0.1.0`），`go get` 只认这个
- **v1.0.0 之前 API 可自由变更**（v0 不受兼容性承诺约束）——要充分利用这个窗口把 API 打磨定型
- 一旦发布 `v2`，module path 必须加 `/v2` 后缀。**因此 v1.0.0 是一道必须谨慎跨过的门**

## 已完成的版本

### v0.1.0 —— 规则数据层

超出初稿的部分：`refdata/live` 的定期自动拉取与**规则变更检测**、费率表的
`WithRate` / `WithLevel` 覆盖、确定性快照持久化、`cmd/refdata-sync`。

### v0.2.0 —— 逐仓永续核算

买卖模式与开平仓模式**都已支持**（原计划只做前者，但仓位状态机同时处理两者
几乎不增成本，且模拟盘账户本身就是开平仓模式，对拍需要）。

公式一律先在模拟盘标定再写代码，这一版标定出的规则见
[okx-rules.md](./okx-rules.md) 各节。

### v0.3.0 —— 预下单计算与内置撮合

内置撮合最实在的价值是**成交角色由模拟器判定**：挂住后被触发是 maker，
下单即成交是 taker，这一项直接决定手续费。手工灌 `Fill` 的路径继续完整可用。

### v0.4.0 —— 资金费与逐仓强平

强平的结算方式曾按「成交于费后破产价、罚金为零」建模，净效果与真实一致但四个
字段全对不上。照一次真实强平重写后才对齐——这件事直接催生了「净效果相同不等于
字段相同」这条设计原则。

### v0.5.0 —— 全仓

先在模拟盘标定再写代码这一条，这一版的回报最大。全仓与逐仓不是同一套账务的参数
差异，而是两套记账方式，凭推断几乎必错。超出初稿的收获：

- **档位表的键必须带 `instType`**。原以为同一 `instFamily` 下永续与交割合并查档，
  实测两者的一档上限折合标的币差 8 倍、mmr 差一倍、杠杆上限差 2.5 倍——不可能是
  同一条阶梯。此前 README 与 `TierKey` 的注释都写错了，已改正
- **全仓强平价有闭式解**，且是逐仓公式的推广；但没有逐仓那一个 tickSz 的缓冲
- **`bePx`（盈亏平衡价）** 顺手标定出来了，与 OKX 逐位相同
- **`MaxSize` 在全仓下少扣了一项**，高估最多 3.3 倍——这是标定过程中发现的既有缺陷，
  不是新功能
- 修掉 `BalanceView.IsoUpl` 误填 `Upl` 的问题：此前两者恒等，有全仓后才会分离

## 排期变更记录

按发生顺序。每条都注明缘由，便于日后判断当时的取舍是否仍然成立。

| # | 变更 | 缘由 |
|---|---|---|
| 1 | 对拍工具从 v0.8.0 **提前到 v0.2.0** | 推迟会让 v0.2 至 v0.7 全部建立在未经验证的规则理解之上；一旦某处有偏差会被单测一起固化，到 v0.8.0 才暴露时返工面积极大。v0.8.0 的职责相应改为「加固与差异清零」而非「从零建对拍」 |
| 2 | 定期自动拉取从 v0.8.0 **并入 v0.1.0** | 使用者指出 OKX 规则与用户费率等级都会变，「可定期自动拉取 + 部分参数可调」本就是规则数据层的形态。按初稿先做静态快照，后面加自动刷新时 Provider 的接口形态要重做 |
| 3 | 预下单计算与挂单冻结**提到 v0.3.0**，全仓顺延 | 使用者指出本库的核心用途是供回测引擎调用，而引擎每根 K 线都要问「这单挂得起吗、能挂多少、成交后会怎样」；追加保证金这类操作在策略回测里可能整个跑完都用不上一次。这个判断是对的——`Balance.OrdFrozen` 此前虽有字段却恒为零，是漏掉的真实缺口 |
| 4 | 撮合从「可选子包」改为**内置** | 使用者指出撮合是每个引擎都要做的事，各自重写一遍既浪费又容易在成交角色、冻结释放这类细节上出错。原 v0.6.0 的「订单层」大部分随之完成，剩余的算法单独立为 v0.7.0 |
| 5 | 资金费与强平**提到 v0.4.0**，全仓再次顺延 | 按对回测结果的扭曲程度排序：忽略资金费会系统性高估持仓收益，不模拟强平会让本该爆仓的策略产出幻想结果；全仓影响的是资金效率，量级小得多。依赖上也顺——逐仓强平是仓位级、自成一体，全仓强平是账户级，放在全仓那一版一并做 |
| 6 | v0.5.0 的验收改为**币种级**而非账户级 | 原写「全仓账户级风险指标与模拟盘一致」，实测发现 `acctLv=2` 下账户级的 `adjEq`/`availEq`/`imr`/`mmr`/`mgnRatio` **恒为空串**——风险按结算币种分别核算，不做全账户折算。跨币种折算是 `acctLv=3` 的事，本就排除在 v1.0 之外。验收标准随之改为币种级 |

## 覆盖缺口

以下功能**已实现但未纳入自动对拍**，或**受外部条件限制**。都在代码注释与
相关文档中就近标注，不靠这一张表兜底。

| 项 | 状况 |
|---|---|
| **资金费** | 结算机制已按真实账单逐条验证，但 OKX 的历史费率只保留约 3 个月（实测四个合约全部截止在同一天，距今 97 天）。超出该窗口的回测取不到真实费率，须自行接第三方数据源、用常数近似或不计资金费。模拟器不产生费率——那是市场结果，回测预测它与预测价格无异。`Bar.Funding` 留空即不计 |
| **逐仓保证金增减** | 规则已由直接探测标定并有单测覆盖，但不在对拍工具的比对范围内：所用 SDK 尚未封装 `POST /api/v5/account/position/margin-balance`，也没有导出通用的已签名请求方法。为一个接口手写 HMAC 签名会把安全敏感代码复制一份出来、日后必然漂移。待 SDK 补上后纳入 |
| **阶梯减仓（逐仓）** | 依 OKX 的阶梯档位规则实现，尚未实测。触发它需要跨越多个档位的仓位，已在模拟盘布好二档纵深的双向仓位等待 |
| **阶梯减仓（全仓）** | **未建模**，一律全平该结算币种的全部全仓仓位。真实 OKX 在全仓下也会先做阶梯减仓，结果比全平温和；本实现偏保守，回测里表现为高估爆仓的杀伤力而非低估 |
| **全仓强平的结算方式** | 触发判据可靠（保证金率经 13 个真实快照核对），但触发之后如何了结未实测——真实全仓爆仓需要不带对冲的裸仓位吃掉整个币种的现金，模拟盘资金规模不足以在可控时间内复现。当前是从已实测的逐仓强平平移过来的 |
| **挂单是否计入全仓查档张数** | OKX 确实把挂单算进了币种级 `imr`/`mmr`，但样本中持仓已在二档、挂单也按二档计，无从分辨。当前按现有持仓合并后的档位算，不计挂单张数 |
| **反向合约的资金费** | 形态由名义价值公式推得（`Q/结算价 × 费率`，单位是标的币），但未单独实测——验证它要等一次真实结算，周期 8 小时，且账户须在结算时刻持有反向仓位。正向的形态已由 20 条真实账单逐位确证 |
| **费率组优先级** | 现有数据下两条解析路径给出同一个数字，无从判定。采用的是使用者拍板的选择，并有守卫测试在两条路径开始分歧时报警 |

## 明确排除在 v1.0 之外

- **组合保证金模式 acctLv=4** —— MMR 由压力测试矩阵得出，工作量约等于其余全部之和
- **跨币种保证金模式 acctLv=3** —— 折算率 haircut、跨币种借币计息、账户整体 USD 折算
- **期权**
- **ADL 自动减仓** —— 排队依赖全市场持仓与收益率，回测环境无法还原
- **假 OKX HTTP 服务端** —— 使用者决定专注 Go 原生 API
