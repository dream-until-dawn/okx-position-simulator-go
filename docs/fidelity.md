# 适用边界与保真度

「近乎 100% 模拟 OKX」这句话，只在明确的条件下成立。本文说清楚那些条件是什么、
已经验证到什么程度、哪些地方是取舍、哪些地方还没有证据。

读这一份，是为了判断**你的策略结果能不能信**。

---

## 一句话结论

**本库还原的是「状态」，不是「过程」。**

给定一笔成交或一根 K 线，仓位与账户会变成什么样——这一部分在下列条件内与 OKX
**逐字段一致**，可视作近乎 100%。

成交本身如何发生——排队、部分成交、滑点——取决于回测引擎喂进来什么，本库
**不建模**，因为没有盘口深度就无从建模，硬造只会给出看似精确、实则杜撰的结果。

---

## 1. 成立的前提

### 账户与合约

| 项 | 覆盖 |
|---|---|
| 账户模式 | **仅 `acctLv=2` 现货合约模式** |
| 持仓方式 | 买卖模式（net）与开平仓模式（long / short），均可 |
| 合约类型 | 永续与交割；正向（linear）与币本位（inverse），四个象限均可 |
| 保证金模式 | 逐仓（isolated）与全仓（cross），均可 |
| 结算币种 | 任意（USDT / USDC / BTC / ETH …），按币种分别核算 |

超出这个范围的（期权、`acctLv=3` 跨币种、`acctLv=4` 组合保证金）不在覆盖内，
见第 5 节。

### 规则数据必须与所模拟的环境一致

内置快照取自**生产环境**。模拟盘的 `tickSz`、杠杆上限与整张档位表都与生产不同
——实测 BTC-USDT 的档位区间相差十倍。用错环境，每个依赖档位、价格精度或杠杆的
计算都会偏，而偏差看起来像模拟器自身的缺陷。

- 回测生产行情 → 用内置快照（`refdata.MustEmbedded()`）
- 对拍模拟盘 → 用 `live.WithSimulated(true)` 从同一环境取

回测请务必用**固定快照**（`Snapshot` 不可变、`Version` 恒定），否则规则在回测途中
变动会让结果不可复现。

### 引擎必须提供的输入

本库不产生行情，缺什么就退化什么。**退化的方式都是显式的**，不会拿一个价格顶替
另一个：

| 输入 | 不提供时 |
|---|---|
| 标记价 `MarkPx` | 退化为开仓均价，未实现盈亏恒为零；强平判据随之失效 |
| 最新价 `Last` | 撮合无从判断，`uplLastPx` 一类按成交价的指标为零 |
| 指数价 `IdxPx` | `triggerPxType=index` 的算法委托**跳过并给出原因**，不拿别的价顶替 |
| 资金费率 `Bar.Funding` | **不计资金费**，等价于零费率 |

⚠️ **不计资金费会系统性高估多头持仓的收益。** 而这也是绝大多数长周期回测的实际
状态——OKX 的历史资金费率只保留约 3 个月（实测四个合约翻到底，全部截止在同一天，
距今 97 天）。超出该窗口须自行接第三方数据源、用常数近似（观测到的费率多为
`0.0001`），或不计。

## 2. 已验证到什么程度

### 全字段对拍（最强的一条）

`cmd/conformance -mode view` 把本库的输出与 OKX 的**原始 JSON** 逐字段比对：
每个字段要么值对得上，要么在 `policy.go` 里写明为什么不建模。两样都没有就判失败。

> **441 个字段：有差异 0，未分类 0。**
> （五个仓位横跨正向/反向 × 逐仓/全仓、两个结算币种，2026-08-31 实测）
>
> 其中约 40 个仅差在精度——OKX 用 float64 计算并截断到 15~17 位有效数字，本库用
> decimal 精确计算，相对差在 `1e-14` 量级。这类差异单独计数而不并进「一致」，
> 是为了让它的规模一直看得见：哪天从 `1e-14` 变成 `1e-6`，说明出了别的问题。
>
> 另有约 10 个余额字段归入「随行情」：它们由标记价推出，而余额与持仓是两次独立
> 的读取，两次之间行情会走。这些字段改用另一种方式验——用余额响应**内部**的字段
> 互验本库的公式（`availBal = 现金 + 全仓浮盈 − imr` 等），余额响应内部必然自洽，
> 于是完全不受时间差影响。这不是放宽标准：公式写错时差的是百分之几乃至几倍，
> 而漂移只有千分之一。

这条标准在 v0.8.0 之前从未被真正验证过——此前的对拍比的是手挑的十几个字段，
而挑着比永远发现不了「有个字段我压根没建模」。补上的当天就暴露出 35 处差异与
4 个从未建模的字段。

### 分项对拍

以下为 2026-08-31 同一轮对拍的实测结果，账上同时持有五个仓位（正向/反向 ×
逐仓/全仓，两个结算币种）：

| 模式 | 验什么 | 结果 |
|---|---|---|
| `view` | 整个响应的每一个字段 | **441 字段，差异 0、未分类 0** |
| `check` | 任意状态下的风险指标，四个象限 | 33 字段一致 |
| `trade` | 从空仓开始的完整流程 | 42 字段一致 |
| `adjust` | 既有状态上的加减仓，含累计量 | 20 字段一致 |
| `margin` | 逐仓保证金的增减 | 8 字段一致 |

> `trade` 的账户级字段（`cashBal`/`availBal`/`isoEq`/`eq`/`frozenBal`）在账上另有
> 仓位时会被跳过并说明——它们反映整个账户，而模拟器里只有本次开出来的那一个。
> 想连账户级一起验，请在空账户上跑，此时字段数为 66。

### 离线夹具

十份夹具锁住实测数据，每次 `go test` 都会重跑，规则一旦被改动就会失败：

| `close-long-isolated-linear` | 一次完整平仓的 15 笔成交 |
| `cross-position-metrics` | 三个场景、13 个快照的全仓账务与合并查档 |
| `inverse-position-metrics` | 七个币本位仓位样本 |
| `max-size` / `max-size-inverse` | 24 组取价规则样本 |
| `funding-bills` | 20 条真实资金费账单 |
| `inverse-funding` | 反向合约资金费的一次真实结算，逐仓与全仓两条落点 |
| `cross-tier-pending` | 跨档 straddle：开仓挂单计入全仓合并查档，平仓挂单不计入 |
| `algo-close-fraction` | closeFraction 只接受 1，且张数在触发时才定 |
| `cross-mgnratio-pending` | 含挂单时保证金率的分子扣挂单手续费、分母含挂单平仓费 |
| `isolated-margin-reducible` | 逐仓可减额上界的两侧夹逼，两个规模各多轮 |
| `liquidation-full-isolated` | 一次**真实强平**的逐字段记录 |
| `algo-orders` | 一次真实触发的全过程 + 40 次棘轮采样 |

### 文档里查不到、只能实测的规则

二十余条，逐条记在 [okx-rules.md](./okx-rules.md) 并标注证据等级。举几个影响最大的：

- **逐仓强平价含一个 tickSz 的安全缓冲**，全仓没有——少了它，强平价系统性偏乐观
  一个 tick
- **收益率的分母是开仓时的初始保证金**，不是当前保证金——只有在持有数周的仓位上
  才分辨得出
- **逐仓的资金费从仓位保证金扣，不动现金**——记错地方会让逐仓权益与强平价一起算错
- **全仓按 instFamily 合并查档，且按张数绝对值相加**——多空对冲不相抵，**开仓挂单也算在内**，而仓位自身的 `mmr` 字段只报它自己那一档，拿它反推会得出相反结论
- **档位表的键必须带 instType**，永续与交割不共用一张表
- **max-size 取保守值的那一侧，正向与反向相反**
- **降低杠杆要【补】保证金，提高杠杆什么都【不退】**——方向最容易想反。提高杠杆
  确实让所需保证金变小，但 OKX 不把多出来的退回现金
- **选定杠杆也就选定了持仓量的天花板**：一档顶格杠杆开满后再加一张会跨进二档，
  而二档容不下当前杠杆，OKX 直接拒单（51004）而非放行后降档
- **阶梯减仓的罚金按【减仓后】所在档位的维持保证金率算**，不是减仓前的
- **全仓保证金率有个结构性下限** `1/(最高杠杆 × (mmr率 + 吃单费率))`，由档位表锁死
  ——全仓账户不可能在没有不利波动的情况下被强平，且杠杆开得越满离强平越近

## 3. 明确的建模取舍

这些不是缺陷，是在**信息不足时做出的选择**。每一条都写明了方向，好让你判断它对
你的策略是偏乐观还是偏悲观。

### 不建模盘口深度

没有深度数据就无从建模，硬造只会给出看似精确、实则杜撰的结果。因此也就不建模：

| 项 | 本库的做法 | 方向 |
|---|---|---|
| 部分成交 | 委托在被触及时**全额成交** | 偏乐观：真实成交可能只成一部分 |
| 排队位置 | 不建模 | 偏乐观：挂单被触及即认为成交 |
| 滑点 | 成交价取委托价 / 触发价，不加滑点 | 偏乐观 |

> 触发后的滑点有一次实测：`triggerPx=2451.68`，市价单成交在 `2451.67`，
> 低一个 `tickSz`。只有一个样本，且滑点本就取决于当时的盘口深度——本库不建模它，
> 但在夹具里留了守卫，差距超出一个 tickSz 的量级就报警。

**成交角色由模拟器判定**：挂住后被触发是 maker，下单即成交是 taker。这一项直接
决定手续费，是内置撮合最实在的价值。

### 一根 K 线只给区间，不给路径

这是回测特有的问题，真实交易里不存在，因为那里有逐笔行情。

| 项 | 本库的做法 | 方向 |
|---|---|---|
| `last` 类型的触发 | 用 `[Low, High]` 整段判 | 分辨率最细 |
| `mark` / `index` 类型的触发 | 只有单点值，用「上一步 → 本步」判穿越 | 分辨率更粗 |
| 移动止损的棘轮与触发孰先孰后 | **先按有利极值棘轮，再判触发** | 偏保守：止损触发得更频繁 |

移动止损那一条值得展开：先棘轮等于假定有利的那一段先发生，于是波动大的一根 K 线
更容易触发止损；反过来假定不利的一段先发生，同一根 K 线可能完全不触发。两者都
可能是真实路径，从 OHLC 无从分辨。选前者是因为它对策略更保守——回测里不会凭空
多出一批本该被止损扫掉的长趋势。

### 精度

OKX 用 float64 计算并截断，本库用 decimal 精确计算。全字段对拍中约四十个字段仅差
在这里，相对差 `1e-14` 量级（具体个数随行情变——价格恰好使某个字段两边都落在同一
截断位时，它就算「完全一致」）。方向上本库更准，但**与 OKX 不逐位相同**——若你的
验收标准是逐位相等，这一条要知道。

## 4. 未实测的规则

以下规则**已实现但没有实测证据**：依据 OKX 的文档或从已验证的公式推导而来。
它们都在代码里就近标注，也列在 [okx-rules.md §12](./okx-rules.md)。

| 规则 | 状况 | 对结果的影响 |
|---|---|---|
| **阶梯减仓（全仓）** | 逐仓那条**已于 2026-08-31 实测确证**（见 okx-rules.md §7）；全仓这条仍未建模，一律全平该币种 | 偏保守：真实 OKX 会先减仓，结果比全平温和 |
| **全仓强平的结算方式** | 触发判据可靠（保证金率经 13 个真实快照核对），但触发之后如何了结未观察到——真实全仓爆仓需要不带对冲的裸仓位吃掉整个币种的现金，模拟盘资金规模不足以在可控时间内复现 | 结算方式是从已实测的逐仓强平平移的 |
| **费率组优先级** | 现有数据下两条解析路径给出同一个数字，无从判定。有守卫测试在两条路径开始分歧时报警 | 当前无差异 |
| **算法委托的部分成交** | 未建模触发后限价单只成交一部分时的 `partially_effective` 状态 | 依赖部分成交，而本库明确不建模部分成交 |

## 5. 明确不覆盖

| 项 | 原因 |
|---|---|
| **期权** | 定价与希腊字母是另一套体系 |
| **跨币种保证金 `acctLv=3`** | 需要折算率 haircut、跨币种借币计息、账户整体 USD 折算 |
| **组合保证金 `acctLv=4`** | MMR 由压力测试矩阵得出而非查表，工作量约等于其余全部之和 |
| **ADL 自动减仓** | 排队依赖全市场持仓与收益率，回测环境无法还原 |
| **现货与币币杠杆** | 本库只做衍生品 |
| **借币与计息** | 是 `acctLv≥3` 的能力 |

这些不是「以后再做」，是**明确排除在 v1.0 范围之外**的决定，见
[roadmap.md](./roadmap.md)。

## 6. 自己验一遍

不必相信这份文档，可以自己跑：

```
cd cmd/conformance
go run . -mode view                     # 全字段对拍，不交易
go run . -mode check                    # 核对现有仓位的风险指标，不交易
go run . -inst BTC-USDT-SWAP -lever 5   # 真实下单后逐字段对拍
go run . -mode adjust -sz 0.2           # 在现有仓位上加减仓
go run . -mode margin -inst ETH-USDT-SWAP -sz 2   # 逐仓保证金增减
```

前两种只读，随时可跑。后三种会真实下单，请在模拟盘上执行。

离线部分直接 `go test ./...`——十份夹具锁住的实测数据每次都会重跑。
